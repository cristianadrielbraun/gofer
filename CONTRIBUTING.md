# Contributing to Gofer

Thanks for helping. This page lists the rules Gofer's code already follows, so a pull request can be merged as it is, without a second round of changes on top. Most of them come from things we had to fix after merging.

If you use an AI coding agent, point it at this file before it starts. The rules apply to its output the same way.

Gofer is pre-1.0 and changes fast, so we're strict about consistency for now. If a rule here gets in the way of a good change, say so in the issue or PR and we'll talk about it.

## Before you start

- **Open an issue first for anything bigger than a bug fix.** Say what you want to change and how it would look. A short "would you take this?" saves both of us a PR that won't be merged.
- **One change per pull request.** A fix, a feature and a docs update are three PRs, not one. Don't add refactors, renames or formatting changes to code you didn't otherwise need to touch.
- **No hidden settings.** Don't add an environment variable or flag that only people who read the code would know about. If Gofer can detect the case itself, detect it. If you can't work out how, open an issue with a sample and we'll find a way.
- **Existing installs keep working the same.** A new behavior that changes what current users see is either opt-in or clearly described in the PR, so it can go in the release notes.
- **Some ideas we'll likely decline:** custom branding and white-labeling, and changes that make one screen behave differently from the rest of the app (for example, "mark as read" meaning something else in one view).

## Product rules

- **Every account type.** Gofer works with IMAP/SMTP, Gmail, Outlook, JMAP, CardDAV/CalDAV and Local folders. A feature should work for all of them, or explain in the PR why it can't. An IMAP-only feature usually needs another look.
- **Think about the whole app.** If you hide, rename or remove something, check everywhere it shows up: the sidebar, search, mail rules, the Move dialog, folder pickers, profile export, notifications.
- **All three styles, light and dark, and phones.** Classic, Minimal and Express each have their own CSS (`assets/css/themes/`). Check your change in all three, in dark mode, and at phone width.
- **Selection and safety.** Actions on mail act on the current selection when there is one. Anything that can't be undone, such as deleting from Trash or signing people out, asks first in a dialog that says exactly what will happen.
- **Admins set the minimum, users can only add to it.** A user's own security setting can make their sign-in stricter than the admin's, never looser.

## Development setup

- Go version: whatever `go.mod` says (currently 1.27.1).
- Tools: [Task](https://taskfile.dev/), [templ](https://templ.guide/), the Tailwind CSS v4 CLI, and Node (only to run the JS tests).
- `task dev` starts Gofer with templ and Tailwind in watch mode at `http://localhost:9090`.
- Generated `*_templ.go` files are committed. Commit them together with the `.templ` change, generated by the templ version in `go.mod`, with Unix (LF) line endings. On Windows, set `git config core.autocrlf input` first.
- `assets/css/output.css` and `assets/min/` are build output and are not committed.
- Keep your branch up to date with `master`. If the generated templ files conflict, regenerate them, don't merge them by hand.

## UI

### Use the components we have

- **Build controls only from the templUI components in `components/`**: `selectbox` for dropdowns, `switch`, `checkbox`, `radio`, `dialog`, `button`, `input`, `popover`, `tooltip`, `toast`, and the others in that folder. Never use a native `<select>`, `<datalist>` or a hand-made dropdown. (A few native selects in older admin pages are not a pattern to copy.)
- The files in `components/` have been changed for Gofer. If a component is missing something, extend it there. Don't reinstall it with the templUI CLI, which overwrites those changes, and don't write a parallel version.
- Icons come from the `icon` component (Lucide). Express also has its own pixel icons in `assets/icons/express/`. If you add an icon to a place that has an Express version, add that too.
- **Reuse what's already on screen.** If a new screen looks like an existing one, such as a folder row, a picker or an account menu, reuse that code and generalize it if needed. Don't copy its markup into a second version that will drift apart. When we say "like the Folders dialog", we mean the same features too, not just the same look.
- Before adding a new place for a feature (a new wizard step, a new tab, a new button on a card), look for the existing place it belongs. Per-account options go in the account's three-dot menu. The account wizard only covers Mail, Contacts and Calendar.

### Settings layout

Settings are cards. Each card has a small uppercase title and a description, and then rows. Each row has its **title and description on the left and the control on the right**. On phones the control goes under the text:

```templ
<div class="settings-card bg-card rounded-lg border p-6 space-y-5">
	<div>
		<h3 class="text-sm font-semibold text-muted-foreground uppercase tracking-wider mb-1">{ i18n.T(ctx, "settings.example.title") }</h3>
		<p class="text-xs text-muted-foreground">{ i18n.T(ctx, "settings.example.description") }</p>
	</div>
	<div class="settings-row border-t border-border/60 pt-5 flex flex-col gap-4 sm:flex-row sm:items-center sm:justify-between">
		<div class="min-w-0">
			<h4 class="text-sm font-medium text-foreground">{ i18n.T(ctx, "settings.example.option_title") }</h4>
			<p class="text-xs text-muted-foreground mt-1">{ i18n.T(ctx, "settings.example.option_description") }</p>
		</div>
		<div class="w-full sm:w-44 shrink-0">
			<!-- selectbox, switch, button… -->
		</div>
	</div>
</div>
```

`internal/views/settings.templ` has many examples (`SettingsComposeDisplayTab`, `textWeightSettingRow`).

- On/off settings are a `switch` on the right, not a checkbox.
- Ordinary settings apply as soon as they change. There's no Save button.
- Settings with consequences, such as security changes that sign sessions out, use a "Confirm change" button and a confirm dialog that says who is affected.
- Dropdowns in settings use `selectbox` with `Class: "mobile-sheet"` on the content, so they open as a sheet on phones.

### Dialogs

- Use templUI `dialog.Header` at the top and `dialog.Footer` with the buttons at the bottom. Both stay fixed and only the body between them scrolls. The `dataActionDialog`, `dataDialogScroll` and `dataDialogFooter` helpers in `internal/views/export_import_tab.templ` do this. Footers have no top divider.
- Long content has to scroll inside the dialog and never push it past the window, at phone width too.

### Accessibility and keyboard

- Labels and `aria-label`s use the name people see, such as the account or folder name, not an internal ID or an address.
- Toolbars are one Tab stop, and the arrow keys move between their buttons. Focused items show the theme's focus ring.
- Don't move focus away from where the user is typing (for example, a signature loading must not take focus from To).

### JavaScript and CSS

- Pages are rendered on the server with templ, and htmx updates them. Use JavaScript for behavior, not for building markup that templ could render.
- Find elements by `data-*` attributes, not by Tailwind classes.
- In `assets/js/app.js`, state that startup code reads must be declared before the `setup*()` calls that use it. A `var` declared further down is still `undefined` at that point and stops the app from loading.
- Use Tailwind classes and the theme's color tokens (`bg-card`, `text-muted-foreground`, `border-border`, …), never fixed colors, so custom themes and dark mode work. Shared CSS goes in `assets/css/input.css`, and style-specific CSS goes in its theme file.

## Text and translations

- Every string people see goes through i18n: `i18n.T(ctx, "key")` in Go and templ, and `goferT("key")` in JavaScript. That includes error messages from the server that end up on screen.
- Add every new key to **all** catalogs in `internal/i18n/locales/` (en, es, pt-br, zh-cn). `go test ./internal/i18n` fails if one is missing. If you can't translate, say so in the PR and we'll do it, but don't leave a key out.
- Use the words in `internal/i18n/GLOSSARY-*.md` for core terms.
- Write plain, everyday words. Say "authenticator app code", not "TOTP", and "sign in", not "authenticate". Say what happens, not how it works inside.
- Descriptions must be true for every account type. Don't write "IMAP folders" in a setting that also applies to Gmail.

## Database

Gofer uses SQLite (`modernc.org/sqlite`). The schema has a single version number, and each change gets the next one.

To change the schema:

1. Update `internal/storage/schema.sql`, which is what new installs get.
2. Write a `migrateVNToVN+1(db *sql.DB) error` function in the storage file for that feature (see `migrateV143ToV144` in `account_sender.go`). It must:
   - run in one transaction and return early if the version is already reached,
   - be safe to run twice (check that a table or column exists before adding it, and use `CREATE TABLE IF NOT EXISTS`),
   - handle old databases that don't have the table at all,
   - finish with `markSchemaVersion(tx, N+1)`.
3. Call it from the migration chain in `internal/storage/storage.go` and raise `CurrentSchemaVersion`.
4. Update the per-user storage migration (`user_storage_migration_preflight.go` and `user_storage_migration_inventory.go`) so it accepts the new version and copies new columns.
5. Add a test that sets up the old schema, runs the migration twice and checks the result.

Also:

- **No schema work on every start.** All schema changes go through a numbered migration. Don't use code that checks and fixes the schema each time Gofer starts.
- **Slow migrations show progress.** If a migration rewrites or recounts a lot of rows, do it in batches and log `N/total` after each one, then a final "done in Xs" line. A big database can take minutes, and the log must show that it's still working.
- **Upgrades are one-way.** After a schema bump, older Gofer versions refuse the database. Mention the bump in the PR so the release notes can warn about it.
- If two PRs take the same schema number, the second one is renumbered when it's merged. Expect that and don't take it personally.
- Don't add database writes to every sync or every request unless the feature really needs them.
- Queries use placeholders (`?`), never string formatting with values in them.

## Go code

- Errors: return them with context (`fmt.Errorf("load folders: %w", err)`) and handle them where something useful can be done. Don't ignore results, such as a JMAP `notDestroyed` or an IMAP `NO` after a copy or move.
- One failing account must not stop work for the others. Log it, mark it and move on.
- Tell temporary failures from permanent ones. A 4xx SMTP reply or a timeout is not a rejection.
- Never fall back to doing something else quietly. For example, don't put mail in another folder when the one asked for doesn't work. Refuse and say why.
- Each account's credentials are only used for that account and service. Don't reuse one service's password for another unless the account is set up that way.
- Comments explain why, in full sentences. Exported functions get a doc comment that says what they do, including edge cases ("An unknown account is sql.ErrNoRows").
- Run `gofmt`. Keep new code in the package and file that already handle that area. Don't create a `utils` package for one helper.

## Tests

- **Every fix comes with a test that fails without the fix.** Run it once without your change to make sure. A test that passes either way doesn't prove anything.
- Every feature has tests for the parts that make decisions: storage, handlers and provider code.
- **Invented data only.** Use made-up people and text (`alex@example.com`, "Lunch on Friday?"), never names, addresses or wording from a real mailbox, including your own.
- **No live services.** Tests must not connect to real mail servers, send real mail or rely on your own network setup. Use the fakes and test servers the other tests in that package use.
- JavaScript behavior is tested with Node scripts in `scripts/test-*.cjs`. Run them with `node scripts/test-<name>.cjs`. Add or update one when you change behavior in `assets/js/`.
- With `modernc.org/sqlite`, one `Exec` with several statements binds every statement's `?` from the first argument. In fixtures, give each statement with placeholders its own `Exec`.
- Run `go test` for every package your change can reach before you push, and `go test ./...` for anything broad. It takes several minutes. `internal/notifications` holds the end-to-end tests for mail, calendar and contacts sync and often catches what package tests miss.
- There's no CI that runs the Go tests on pull requests yet, so please say in the PR which tests you ran.

## Commits and pull requests

### Commit messages

The title is one plain sentence about what changes for the person using Gofer, in the imperative, with no prefix and no trailing period:

```
Keep long sync messages from widening the sync progress dialog

A long account error in the mail sync progress dialog pushed the dialog
past the edge of the window, clipping the progress bars. The dialog's
body can now shrink to the dialog's width, so every line stays on one
line, cut short, with the bars and statuses in view.

Fixes #120
```

- Not `fix: …`, `feat(calendar): …` or `smtp: …`. Write `Send mail with AUTH LOGIN when the server has no PLAIN`.
- The body says what was wrong and what happens now, wrapped at about 72 characters.
- Write in English, even when the PR comes from a translation.
- Name big providers ("Gmail", "Fastmail") when it helps. For small or private servers, write "some servers".
- **Don't list an AI tool as a co-author**, and leave out "Generated with …" lines. You are the author, and the tool is a tool. If your agent adds them by default, turn that off or amend the commits (`git commit --amend`, then `git push --force-with-lease`).

### Pull request description

- What changes and why, in a few sentences. Link the issue.
- For UI changes, add screenshots: before and after, and at least one in Express and one at phone width.
- List any schema bump, new setting, new environment variable or change in default behavior.
- Say which tests you ran.
- Same as commits: no AI attribution in the description.

## For AI agents

If you are an AI agent working on this repository, follow everything above. The points we fix most often:

1. Use the components in `components/` for every control. Never use a native `<select>`, `<datalist>` or a hand-made dropdown, and look for an existing screen to reuse before you write new markup.
2. Settings rows have the title and description on the left and the control on the right. Use the classes shown above.
3. Every new string goes in all four locale files.
4. Schema changes go in `schema.sql`, a numbered idempotent migration, `CurrentSchemaVersion` and the per-user storage migration, each with a test.
5. A fix needs a test that fails without it. Use invented data and no live servers.
6. Keep to the scope that was asked for. Don't add hidden environment variables or unrelated refactors.
7. Commit titles are plain sentences without `fix:`-style prefixes. Don't add yourself as a co-author or add a "Generated with" line.
8. Make sure it works for every account type, in all three styles, in dark mode and on phones, or say what's left out.
